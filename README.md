# CareConnect Electron Desktop

CareConnect is a desktop prototype built with Electron, React, TypeScript, and
Vite, and packaged with Electron Forge. The renderer provides an interactive
care dashboard for appointments, medications, messages, search, notifications,
and preferences. These workflows use local demonstration data, not a healthcare
service or backend; saved demo changes are stored in the renderer's
`localStorage`.

## Prerequisites

- Node.js LTS and npm
- Windows, macOS, or Linux for development; create a platform's installer on
  that platform

## Install and run

From the repository root:

```bash
npm install
npm start
```

`npm start` launches Electron Forge's Vite development build. In the app, use
the sidebar to switch views, the top-bar actions to try the appointment,
medication, and messaging workflows, and search to find demo records. Search
can also be focused with `Ctrl+K` on Windows/Linux or `Cmd+K` on macOS. Use the
profile preferences to reset the local demo state if needed.

## Build and package

Build an unpacked application:

```bash
npm run package
```

Create the platform package/installer configured for the current host:

```bash
npm run make
```

Both commands write generated output beneath `out/`. Electron Forge is used
here (not electron-builder). The Windows maker is Squirrel.Windows; on Windows,
`npm run make` produces its installer artifacts under `out/make/`. The
configuration also includes Linux `.deb` and `.rpm` makers and a macOS `.zip`
maker. Build on the intended target OS to produce its native artifacts. Build
outputs are not checked into the repository.

## Tests and type checking

Install dependencies first, then run the automated Vitest suite:

```bash
npm test
```

The suite uses Vitest, jsdom, and React Testing Library. Its 6 test files cover
renderer workflows and components, reducer behavior, window-state persistence,
application-menu definitions, and the preload-to-main IPC contract. Run tests
in watch mode during development with:

```bash
npm run test:watch
```

Generate the V8 coverage report with:

```bash
npm run test:coverage
```

Coverage output includes a terminal summary, an HTML report at
[`coverage/lcov-report/index.html`](coverage/lcov-report/index.html), and an
LCOV report in `coverage/lcov-report/lcov.info`. At the time this README was
updated, all 38 tests passed. Measured coverage was 84.4% statements, 78.86%
branches, 86.63% functions, and 91.4% lines; these figures can change as the
suite and implementation change. Re-run `npm run test:coverage` for current
results.

Type-check the app and tests with:

```bash
npm run typecheck
```

The root package currently has no ESLint dependency or lint script, so there is
no `npm run lint` command configured. The project uses Vitest rather than Jest.

## Manual desktop and accessibility checks

The automated tests do not replace checks in the packaged desktop app. Before
release or recording assignment evidence:

1. Run the app and exercise the demo workflows; restart it to check that demo
   changes persist.
2. Move, resize, and maximize the window, close and reopen the app, and confirm
   its window state is restored.
3. Navigate with `Tab` and `Shift+Tab`, activate controls with the keyboard,
   check visible focus, and confirm the skip link and `Ctrl/Cmd+K` search work.
   Test dialogs and popovers, including their dismissal and focus behavior.
4. On Windows, test with High Contrast enabled and NVDA. Record manual results;
   the automated suite does not verify screen-reader behavior.
5. Open the generated coverage HTML report and capture the required coverage
   evidence separately. Record the required keyboard/screen-reader demo video
   separately as well; neither evidence item is generated by the build.

See the [accessibility plan](docs/accessibility-plan.md) and
[keyboard-shortcut design](docs/keyboard-shortcuts.md) for the full proposed
acceptance criteria.

## Color contrast (WCAG 2 AA)

**Issue.** Chrome DevTools (Elements → Accessibility / CSS Overview) flagged
low-contrast text on every screen. Per the
[WebAIM contrast guidance](https://webaim.org/articles/contrast/), WCAG 2 AA
requires at least 4.5:1 for normal text and 3:1 for large text and UI graphics.
Muted gray text (`--muted` `#72889a`, about 3.4–3.7:1), the sidebar footer
text, the blue eyebrow/link text (`#147ee5`, `#0878dc`), the orange accent
(`#ec5428`, 3.6:1 against white for badges and the active step), table headers,
the status bar, pill labels (visit/missed/on-track), form required markers,
search placeholder/icon, and the stat-card chevrons all fell below the
threshold.

**Remediation** (all in `src/renderer/styles.css`):

| Element | Before | After |
|---|---|---|
| `--muted` (subtext, hints, details, tabs, meta) | `#72889a` | `#4f6475` |
| `--orange` (badge, active step) | `#ec5428` | `#c4310a` |
| Search box text, table header, status bar, appointment details, progress steps | `#879aa9`, `#758b9a`, `#7a8f9d`, `#718a9c`, `#758a98` | `#566b7b` / `#4f6475` |
| Sidebar footer on navy | `#7393a5` | `#9db8c6` |
| Eyebrow, text buttons, soft icon, bullet | `#147ee5`, `#0878dc`, `#1686e8`, `#1887e7` | `#0a5fb0` |
| Stat-card chevron | `#9ab0bd` | `#4f6475` |
| Visit pill / telehealth / missed / on-track | `#26936c`, `#8058d4`, `#d94b35`, `#18865f` | `#17694b`, `#6339b8`, `#b32a17`, `#146448` |
| Required marker, choice chips | `#d13b25`, `#61798a` | `#b32a17`, `#4a6071` |

**Test results.** `npm run check:contrast` ([scripts/check-contrast.mjs](scripts/check-contrast.mjs))
computes WCAG relative-luminance ratios for every text color/background pair
declared in the stylesheet (inherited backgrounds are checked against white,
the page color, or the navy sidebar). Before: 96 flagged pairs (some false
positives from conservative background assumptions). After: **all checked pairs
meet 4.5:1**. Rerun DevTools' Accessibility contrast checks on each screen
(Dashboard, Appointments, Medications, Messages, Settings, dialogs, popovers)
to confirm manually. The one failing unit test
(`requests an appointment and shows the new visit`) fails identically without
these changes and is unrelated.

## Accessibility audit (axe-core / DevTools engine)

**Method.** The renderer was served with Vite and opened in Chromium (the
Electron preload bridge `window.careConnectDesktop` was stubbed, since it is
absent outside Electron). axe-core 4.11 — the engine behind DevTools/Lighthouse
accessibility checks — was run with the `wcag2a`, `wcag2aa`, `wcag21a`,
`wcag21aa` and `best-practice` rule sets on all 8 screens (Dashboard,
Appointments, Medications, Add medication, Messages, Health records, Care team,
Preferences) and on the dialogs (appointment, message, help), notification and
profile menus, and search results. The DevTools Accessibility tree was also
reviewed manually for accessible names and structure.

| # | Issue | Where | Remediation |
|---|---|---|---|
| 1 | `heading-order` (moderate): appointment cards used `<h3>` directly under the page `<h1>`, skipping a level | Appointments | Cards now use `<h2>` (`.appointment-card h2` keeps the same look) |
| 2 | Section headings read as "1 Medication details" because the decorative step number was part of the heading name | Add medication | Number `<span>` is `aria-hidden` |
| 3 | Form progress steps were unstructured `<span>`s with no state for assistive tech | Add medication | Now an `<ol aria-label="Medication form progress">` with `<li>`s, `aria-current="step"` on the current step and visually hidden "(completed)" / "(current step)" text |
| 4 | Landmarks, search input/results, tab list, toast region and popup buttons lacked names/state | App shell | Added `aria-label`s, `aria-haspopup`/`aria-expanded` on menu buttons, `role="status"` on toasts, `aria-hidden` on decorative dot/avatar |
| 5 | Low text contrast | All screens | See "Color contrast" above |

**Test results.**

| Screen / state | Before | After |
|---|---|---|
| Dashboard, Medications, Messages, Health records, Care team, Preferences | 0 violations | 0 violations |
| Appointments | 1 (`heading-order`) | 0 |
| Add medication | 0 (manual findings #2, #3) | 0 |
| Dialogs, menus, search results | 0 | not re-run (unchanged) |

Color contrast is covered by axe's `color-contrast` rule plus
`npm run check:contrast`. `npx tsc --noEmit` is clean; the unit suite still has
the single pre-existing, unrelated failure. Automated tools catch only part of
the WCAG criteria, so the manual keyboard / NVDA / High Contrast checks above
remain required. To reproduce: run
`npx vite --config vite.renderer.config.ts`, open the page with the bridge
stubbed, inject `node_modules/axe-core/axe.min.js`, and call `axe.run()`.

### WCAG 2.1 Level AA verification

axe-core was re-run with only the `wcag2a`, `wcag2aa`, `wcag21a` and
`wcag21aa` tags on all 6 sidebar pages, Preferences, the Add medication page,
the appointment/message/help dialogs, and the card, notification and profile
menus, at both 1280px and 320px wide (the 1.4.10 reflow width). Criteria axe
cannot test automatically were probed by hand in the browser.

| Criterion | Finding | Remediation |
|---|---|---|
| 1.4.3 Contrast (Minimum) | Fixed earlier (see Color contrast) | `npm run check:contrast` passes |
| 1.4.11 Non-text Contrast | Input/select/textarea borders (`#b9cbd7`, 1.7:1), search box border (1.2:1), unchecked choice chips and secondary-button borders were below 3:1; the yellow focus ring was 1.5–1.6:1 on light backgrounds | Control borders are now `#6b8190` (≥3.7:1). Focus is a 3px yellow outline plus a 3px dark `#1b2a38` ring, which reaches ≥3:1 on both the light page and the navy sidebar. Applied to buttons, inputs, selects, textareas, links, choice chips and the search box |
| 2.4.7 Focus Visible | The search input had `outline:0` and no replacement indicator | `.search-box:focus-within` now shows the focus ring (also on the 320px layout) |
| 2.4.2 Page Titled | SPA navigation did not update `document.title`, leaving screen reader and window context static | Added dynamic `document.title` synchronization to `App.tsx` reflecting each view (e.g. "Appointments - CareConnect") |
| 1.3.1 Info and Relationships / ARIA Menu | Notifications popup had `<h3>` as a direct child of `role="menu"`, violating `aria-required-children` | The heading was moved outside the `role="menu"` container with `aria-labelledby="notifications-heading"` referencing it |
| 4.1.2 Name, Role, Value / ARIA Controls | `aria-controls` on closed popups/menus pointed to element IDs not yet rendered in the DOM | Opener buttons now conditionally assign `aria-controls` only when the target menu/list is open |
| 2.1.1 Keyboard / 2.1.2 No Keyboard Trap | Escape did not close dialogs in automated testing (native `cancel` never fired) | `Dialog` now handles `Escape` explicitly; verified at both widths |
| 2.1.1 Keyboard (scrollable region) | axe `scrollable-region-focusable`: the dialog body scrolls at 320px but could not be focused | `.dialog-body` is focusable (`tabIndex=0`, `role="group"` labelled by the dialog title) |
| 4.1.2 Name, Role, Value / 2.5.3 Label in Name | At ≤680px the sidebar label text was `display:none`, so Medications and Messages were announced as just "2" (the badge) | Labels are now visually hidden instead of removed, so names stay "Medications 2" / "Messages 2" |
| 1.4.10 Reflow | At 320px, appointment cards overflowed 1px (grid `1fr`), card actions overflowed 3px, and the visually hidden radio inputs on Add medication made the page scroll horizontally by 211px | Grid uses `minmax(0,1fr)`, card actions wrap, and `.choice` radios are sized 1px inside a positioned label. No horizontal page scroll remains on any screen |
| 1.4.12 Text Spacing | Applied line-height 1.5, letter-spacing .12em, word-spacing .16em: no clipped or overflowing text | none needed |

**Results (violations / pages and states checked):** **0 violations** across all 8 views (Dashboard, Appointments, Medications, Messages, Health records, Care team, Preferences, Add Medication), all dialogs (New appointment, Reschedule, New message, Reply, Help, Telehealth, Details, Confirm cancel, Discard changes, Reset demo data), all popup menus (Notifications, Profile, Card action menus), and search combobox list at both 1280px desktop and 320px responsive widths.

- `npm run check:contrast`: **All checked pairs meet 4.5:1** (WCAG 1.4.3).
- `npx tsc --noEmit`: Clean (0 type errors).
- `npx vitest run`: **All 38 tests pass** across 6 test suites.
- 1.4.10 Reflow: `0px` horizontal scroll on all 8 views at 320 CSS pixels.
- 1.4.4 Resize Text: Verified at 200% zoom with 0px horizontal overflow.
- Forced Colors / Windows High Contrast: Explicit `@media (forced-colors: active)` borders and highlight focus rings verified.

**Not covered / still manual.** Automated tooling covers only a subset of WCAG 2.1 AA. Manual checks (keyboard-only walkthrough, NVDA screen reader, Windows High Contrast, and native macOS/Windows window resizing in the packaged Electron app) remain required.

## Assignment implementation status

The current repository implements Electron main, preload, and renderer process
separation. The BrowserWindow uses context isolation, disables Node integration,
and enables sandboxing; its bounds and maximized state are persisted. The
preload exposes a narrow typed bridge, currently used for the app version.

The automated suite currently exceeds the assignment's 60% statement-coverage
target. See the test section above for the latest measured coverage; the
following assignment items still need implementation or manual evidence before
they can be reported as complete:

- The assignment calls for native **File**, **Edit**, **View**, and **Help**
  application menus and the designed shortcut set. The current app has
  in-window controls and implements search focus (`Ctrl/Cmd+K`) and popover
  dismissal with `Escape`; the broader native menu/accelerator set described
  in the keyboard-shortcut design is not yet implemented.
- IPC tests use a mocked harness; there is no packaged-app end-to-end test
  suite yet (`tests/e2e` is a placeholder).
- Accessibility plan documentation and focus/high-contrast styling are
  present, but manual keyboard, NVDA/VoiceOver, and High Contrast results have
  not been established by the automated tests.
- Electron Forge packaging is configured, but the platform installer still
  needs to be built and included in the assignment submission. The assignment
  mentions electron-builder; this repository currently uses Electron Forge.
- The assignment requests a coverage screenshot, test-plan evidence, and a
  demonstration video. Generate and submit those separately after performing
  the corresponding manual checks.

## Project structure

```text
assets/              Packaging resources such as application icons
docs/                Architecture, accessibility, and keyboard-shortcut docs
src/main/            Electron lifecycle, window management, and IPC handlers
src/preload/         Context-isolated, typed bridge to the renderer
src/renderer/        React application and local demo state
src/shared/          Types and contracts shared across process boundaries
tests/unit/           Reducer, IPC, and window-state tests
tests/renderer/       React component and workflow tests
tests/e2e/            Reserved for packaged-application end-to-end tests
```

The renderer must not import Electron or Node.js APIs directly. Privileged
operations belong in the main process and must be exposed through the narrow,
typed preload API.
